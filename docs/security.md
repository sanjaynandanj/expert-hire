# Security

Implemented controls include password hashing, signed 12-hour HTTP-only/SameSite cookies backed by revocable server-side session records, logout and logout-all, hashed and expiring account action tokens, optional TOTP MFA with AES-GCM-encrypted secrets and hashed single-use recovery codes, hashed scoped API keys with revocation, AES-GCM-encrypted webhook secrets, HMAC-signed webhook delivery with HTTPS/public-address validation and DNS pinning, production secret checks, rejection of seeded `.test` accounts in production, CSRF-oriented Origin/Sec-Fetch-Site checks for state changes, security headers, credentialed CORS allowlists, request IDs, sensitive log redaction, configurable rate limits, tenant predicates, server-side permission checks, hashed/expiring assessment tokens, candidate consent records, advisory integrity events, audit writes, and transactional credit accounting. Candidate code execution remains disabled; the local evaluator and fake checkout cannot handle production activity.

Before production, independently review account recovery, API-key, and webhook handling; protect/back up encryption keys and define rotation procedures; decide whether OAuth is required; complete CSRF/CORS/CSP review, signed private object access, malware scanning, retention/deletion jobs, immutable audit retention, abuse controls, dependency/security scans, incident response, and external penetration testing.

All AI output remains advisory in the user experience. The local scoring provider is a deterministic demo evaluator and is not suitable for candidate ranking or employment decisions. Integrity metadata is review context and must not be interpreted as proof of misconduct. Coding-assessment invites and launch links are rejected, and the worker has a second guard, until an isolated, resource-limited sandbox provider is configured and reviewed; source is never evaluated in the API or standard worker process.
