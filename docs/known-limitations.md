# Known limitations

The application is a working development build. It is not ready for production hiring decisions or handling real candidate data.

- The brand name is temporary and has not had a trademark review.
- Nova has configurable model adapters, persisted bounded tool execution, cited evidence review, historical follow-up discussion with fresh evidence checks, and exact human-approved invitation proposals. Without explicit provider configuration it is disabled, with no simulated AI fallback. Tests currently use injected models or mocked HTTP/API data, not a real configured model. Live-model verification and adversarial evaluation remain pending; MCP is not exposed via organization-only API keys. See [Nova](nova.md).
- Seeded user accounts share a known demo password and are rejected in production; the seed command refuses to run in production. Public registration creates a workspace owner and requires email verification; workspace invitations, password resets, session revocation, optional TOTP MFA, and single-use recovery codes are implemented. Production delivery needs `RESEND_API_KEY` and `EMAIL_FROM`, and MFA requires a stable `MFA_ENCRYPTION_KEY`. OAuth and administrator-assisted recovery when both an authenticator and all recovery codes are lost are not implemented.
- Sessions are signed 12-hour HTTP-only cookies backed by revocable server-side records. Cross-origin state-changing requests are rejected. Production still needs managed secret rotation, full CSRF/CORS/CSP review, secure host configuration, and an external security review.
- Employer jobs, candidates, pipeline, assessments, reports, client accounts, candidate notes, meeting records, basic analytics, staffing placements, and university placement paths use tenant-scoped database records. Meeting invitations are not delivered to external calendars and analytics currently reports live totals rather than historical cohorts.
- Job status, weighted requirements, and assessment rounds are editable in the UI, including questions, thresholds, durations, and proctoring settings. Unused saved rounds can be removed with confirmation; rounds with assessment history are protected by a row lock and usage check. Saved rounds can be retired/restored with audited state conflicts: retirement blocks new invitations without cancelling existing sessions or removing reports. Pipeline stages can be created, renamed, reordered without moving candidates, and deleted only when unused; stale reorder requests conflict rather than overwrite newer orders.
- Client creation, status, fee model, billing contact, and guarantee fields are stored and editable in the workspace. Staffing starts snapshot fees and create draft invoices; issuing and marking them paid is manual, with no tax-compliant documents, accounting-provider integration, bank reconciliation, or replacement guarantee workflow.
- Candidate written drafts are saved to the active assessment with revision checks, restored across devices using the secure launch link, and frozen into the final submission. Demo sessions still use browser-local storage. Save failures require explicit reload after copying unsaved text; there is no offline synchronization or automatic conflict merge. File upload, resume parsing, speech, transcription, real interview scheduling, video, and device-permission checks remain incomplete.
- The local evaluator uses deterministic lexical coverage to demonstrate traceable scoring. It is not an assessment model, has not been validated for job relevance or adverse impact, must not be used to make hiring decisions, and is disabled for production submissions and worker execution.
- New assessment invitations freeze round/question/settings and job/rubric context for launch, evaluation, and reports. Older assessments lack historical snapshots and use current configuration, explicitly marked in the report API. Empty authored plans freeze development fallback prompts; these are not validated job-specific questions.
- Integrity events are coarse browser focus-change context. They do not establish misconduct, and the product never takes an automatic hiring action from them.
- Coding assessments have no isolated execution environment and are fail-closed at invitation, launch, submission, and worker processing. Never execute candidate code on the API or standard worker host.
- University staff can manage seasons, offer policies, companies/recruiter contacts, import invited student rosters, review and approve/decline student academic-profile corrections, reconcile prior placement status/CTC with audited source notes, author/publish drives, review applications, issue offers, and record outcomes; students can request academic-profile corrections, apply to eligible open drives, track application status, view offers, and accept or decline them after accepting an invitation. Unreviewed corrections do not affect eligibility. Offer issuance serializes per-student transactions and enforces the per-season cap. Tenant-scoped in-app notifications cover review decisions, offers, and application updates; email/SMS/push delivery remains unconfigured.
- Candidate practice persists text attempts for three categories (technical reasoning, communication, and behavioral reflection). Resume review, coding execution, speech, pitch, prompt-lab tools, and validated readiness models are not implemented; demo visitors see non-persisted preview data.
- Credits can be read and debited to the immutable ledger. Checkout is a local fake provider; no money is collected and no paid credit grant is wired. Checkout requests fail closed in production until a real provider is integrated.
- Scoped API-key issue/list/revoke/authentication and a public jobs/candidates API with tenant-scoped cursor pagination are implemented. These are live lists, not snapshot exports; internal workspace collections still have fixed limits. Webhooks support encrypted secrets, HMAC signatures, public HTTPS destination validation, queued retryable deliveries, history, and replay. Event coverage is currently limited to candidate, pipeline, assessment, meeting, and placement-application events.
- The S3-compatible local store is SeaweedFS. Production storage, private ACLs, malware scanning, lifecycle retention, and signed file URLs still need implementation.
- Authenticated API/worker Prometheus metrics and scrape/alert examples are implemented. No collector or alert destination is deployed; queue backlog and dependency-latency metrics remain unimplemented. See [operations monitoring](monitoring.md).
- A daily worker retention task deletes expired sessions, account tokens, invitations, and used MFA recovery codes after `EPHEMERAL_RETENTION_GRACE_DAYS` (default 30, allowed 1–365), and clears expired pending assessment launch tokens. It intentionally does not delete candidate responses, assessment evidence, practice history, or audit logs; those require a documented, legally reviewed retention policy. Local Docker services and tests use fictional data. There is no scheduled metrics/alerting stack, production load test, accessibility certification, penetration test, disaster-recovery exercise, or legal/trademark review. Production AI, calendar, billing, and object-storage providers still need selection, credentials, and operational setup.
