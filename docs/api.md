# API

The Fastify API runs at `http://localhost:4000`; interactive OpenAPI documentation is at `/docs`.

Queued candidate submissions persist validated evaluator input before queueing. Redis submission failures/timeouts return HTTP 202 with `processing: pending_queue` and assessment status `PROCESSING`; the non-production worker recovers eligible records at startup and once per minute. Database ownership leases fence late completion writes and cap evaluation attempts at three. Inline submissions are not swept. See [assessment processing](assessment-and-scoring.md) for legacy and production limitations.

Implemented route groups:

- Health: `GET /health`, `GET /ready`
- Authentication: `POST /v1/auth/register`, `POST /v1/auth/login`, `POST /v1/auth/logout`, `POST /v1/auth/logout-all`, `GET /v1/auth/session`
- Account lifecycle: `POST /v1/auth/password-reset/request`, `POST /v1/auth/password-reset/confirm`, `POST /v1/auth/verification/request`, `POST /v1/auth/verification/confirm`, `GET /v1/auth/invitations/:token`, `POST /v1/auth/invitations/:token/accept`, `GET /v1/auth/mfa/status`, `POST /v1/auth/mfa/enroll`, `POST /v1/auth/mfa/confirm`, `POST /v1/auth/mfa/disable`
- Developer platform: `GET/POST /v1/api-keys`, `DELETE /v1/api-keys/:keyId`, `GET/POST /v1/webhooks`, `DELETE /v1/webhooks/:endpointId`, `GET /v1/webhooks/:endpointId/deliveries`, `POST /v1/webhooks/deliveries/:deliveryId/replay`
- Public API (Bearer API key): `GET /public/v1/jobs`, `GET/POST /public/v1/candidates`
- Workspace member invitations: `GET/POST /v1/invitations`, `DELETE /v1/invitations/:invitationId` (owner/admin only)
- Workspace: `GET /v1/workspace`, `GET /v1/dashboard`
- Jobs, candidates, and clients: `GET/POST /v1/jobs`, `PATCH /v1/jobs/:jobId`, `GET/POST /v1/candidates`, `GET/POST/PATCH /v1/clients`
- Unused assessment rounds: `DELETE /v1/jobs/:jobId/rounds/:roundId` (requires `job.manage`, returns 204; any assessment history blocks removal with 409, including concurrent invitation creation)
- Staffing placements and invoices: `GET/POST /v1/staffing/placements`, `PATCH /v1/staffing/placements/:placementId/guarantee`, `PATCH /v1/staffing/invoices/:invoiceId`
- Pipeline: `GET/POST /v1/pipeline/stages`, `PATCH/DELETE /v1/pipeline/stages/:stageId`, `POST /v1/candidate-jobs`, `PATCH /v1/candidate-jobs/:candidateJobId/stage`
- Pipeline order: `PATCH /v1/pipeline/stages/order` with complete `stageIds` and last-loaded `expectedStageIds`; requires `candidate.manage`. Stale order returns 409, invalid/foreign/missing/duplicate IDs return 422. Reorders do not move candidate assignments. Stage creation, removal, and ordering serialize per organization; creation is limited to 200 stages.
- Assessments: `GET/POST /v1/assessments`, `GET /v1/assessments/:assessmentId`
- Candidate session: `GET /candidate/assessments/:token`, consent, start, integrity-events, and submit actions
- Credits: `GET /v1/credits`, `POST /v1/credits/checkout` (local fake checkout only)
- Student preparation and placement: `GET /v1/student/practice`, `PATCH /v1/student/profile` (request academic-profile corrections), `POST /v1/student/practice/attempts`, `GET /v1/student/drives`, `POST /v1/student/applications`, `GET /v1/student/applications`, `PATCH /v1/student/offers/:offerId` (student-owned accept/decline only), `GET /v1/student/notifications`, `PATCH /v1/student/notifications/:notificationId/read`; university reviewers use `PATCH /v1/placements/students/:studentId/profile-correction` to approve or decline pending changes
- Campus placement: seasons and offer policies, company/recruiter configuration, drive authoring/status, overview, student roster import/invitations, historical placement reconciliation, eligibility, applications, application review, offers, and offer outcomes under `/v1/placements`

Authenticated workspace routes require an `X-Organization-Id` header. The API verifies membership and permission on the server before querying tenant data. Candidate launch URLs use 256-bit random tokens; only their SHA-256 hashes are stored, they expire, and successful completion invalidates them.

Staffing starts snapshot the linked client's percentage/flat fee and guarantee terms (job overrides take precedence), calculate a draft invoice, and retain salary and invoice currencies separately. Invoice issue/payment/void transitions and guarantee resolution are audited; payment reconciliation is manual. These are internal records, not tax-compliant invoices or an accounting-provider integration.

`PATCH /v1/jobs/:jobId/rounds/:roundId/retirement` requires `job.manage` and `{ retired, expectedRetired }`. Retirement/restoration is tenant scoped, locks the round against new invitations, and audits actual changes; stale expected state returns 409 and matching no-ops produce no extra audit. Retired rounds remain in role editing/history but are omitted from invitation choices. Existing session links, drafts, and reports are unaffected. Invitations re-check round state/type under the same lock before creating an assessment or debiting credits; retired rounds return `assessment_round_retired` (409). Credit balance updates are serialized per organization.

Assessment invitation idempotency is tenant-scoped and rechecked after acquiring the organization lock. Concurrent identical requests return one 201 creation and a 200 replay referencing the same assessment, with exactly one ledger debit/audit. Only the creation response returns the launch URL; replays return `launchUrl: null` and `Idempotent-Replay: true`. New ledger rows store a SHA-256 request fingerprint covering candidate, round, and expiry duration; changing those details with the same key returns `idempotency_key_conflict` (409). Keys already used for other ledger purposes, or whose original assessment is missing, also conflict. Historical rows without a fingerprint can validate candidate/round only; their original expiry request was not stored. Insufficient balance returns `insufficient_credits` (409) without creating an assessment, ledger entry, or audit.

Errors use `{ error: { type, code, message, request_id } }`. Route-level validation is enforced with Zod. Account action tokens are random, single-use, stored as SHA-256 hashes, and expire. Registration creates an owner membership and requires email verification. MFA uses an authenticator-compatible TOTP secret encrypted with `MFA_ENCRYPTION_KEY`; recovery codes are returned only at enrollment and stored as hashes. Login requires the password plus a TOTP or unused recovery code when MFA is enabled. Development responses include verification action links and attempt delivery to Mailpit; production email uses Resend via `RESEND_API_KEY` and `EMAIL_FROM`.

API keys use `Authorization: Bearer nsk_test_…` or `nsk_live_…`, are scoped per workspace, stored only as SHA-256 hashes, and returned once at creation. Supported scopes are `jobs:read`, `candidates:read`, and `candidates:write`. Webhook secrets are encrypted at rest with `WEBHOOK_ENCRYPTION_KEY` and returned once. Deliveries include `X-Northstar-Event`, `X-Northstar-Delivery`, and `X-Northstar-Signature: t=<unix-seconds>,v1=<hex-HMAC-SHA256>`, where the signed bytes are `<timestamp>.<raw-request-body>`. Verify signatures using constant-time comparison and reject timestamps older than five minutes. Delivery history is retained per endpoint; transient failures retry with exponential backoff, terminal failures can be replayed, and the worker periodically re-enqueues due pending rows to recover from a process exit between database persistence and queue submission. Only public HTTPS destinations on port 443 are accepted; DNS answers are checked and a validated address is pinned for the TLS request to mitigate SSRF and rebinding.

Public jobs/candidates lists accept `limit` (1–100, default 100) and `cursor` (the previous response's `next_cursor`). Responses include `data`, `has_more`, `next_cursor` (null at the end), and `total_count` for the complete tenant-visible list, not just the page. Follow cursors until `has_more` is false. Ordering is descending creation timestamp then ID, so equal timestamps do not skip or duplicate records. Cursors are resolved inside the API key's workspace and, for jobs, only against open roles. Foreign, missing, deleted, or no-longer-visible cursors return the same `invalid_cursor` 422 response; restart the list. Invalid page sizes return `invalid_pagination` 422. Lists are live, not point-in-time export snapshots: new records before the cursor require a later refresh, and totals can change while paginating.

Public candidate writes upsert by normalized email within the key's workspace: creation returns 201 and an existing candidate returns 200. Creation emits `candidate.created`; actual name/headline changes emit `candidate.updated` with `changed_fields`. Repeating unchanged details emits no additional event. Candidate writes, key-attributed audits, and delivery records commit atomically; workspace candidate creation has the same atomic guarantee. Payloads contain identifiers and source, not candidate names/email or API secrets. New webhook envelopes include numeric `version: 1`; previously stored payloads without a version retain their original bytes on replay.

Queue submission is bounded to three seconds and a rejection/timeout leaves committed deliveries `PENDING` for the worker's periodic recovery sweep, rather than falsely marking them terminally failed. Replays are audited and atomically transition from failed to pending; competing replay requests produce one acceptance and one 409. Retained finished queue jobs are removed before resubmission using a stable delivery job ID; the database delivery history remains intact. Receivers must deduplicate by event ID because delivery is at least once.

Delivery workers claim rows atomically with a unique, 60-second lease. Results can be saved only by the current, unexpired lease owner. The minute-based sweep recovers expired processing leases (including legacy rows without a lease); attempts remain counted in PostgreSQL across worker restarts and queue-job recreation. After six claims, an exhausted delivery becomes `FAILED` and requires an authorized, audited manual replay. Replay resets the attempt budget and clears lease state. A worker crash after a receiver accepts a request can still cause a repeated request: lease ownership prevents stale database writes, not duplicate external effects.

Destination validation has an eight-second wall-clock deadline. Delivery uses one eight-second budget for DNS, connection/TLS setup, and response headers, aborting the request on expiry; internal overrides are restricted to 1–30,000 milliseconds, below the worker lease. Receiver response bodies are discarded and the connection closed after the status is read. OS DNS work cannot be cancelled, but a late lookup cannot start an outbound request. Redirects are not followed.

All currently emitted events persist inside their business transaction: candidate writes, candidate/job assignments, pipeline movements, meetings, student/staff placement applications, and inline/worker assessment completion. Repeating a pipeline move to the current stage produces no extra audit/event. Assessment completion locks the assessment and saves outcome, evidence, audit, and event together; concurrent or retried completion returns the existing result without duplicating evidence/events. Submission claims `IN_PROGRESS` atomically. Application creation serializes capacity checks per drive. Event coverage beyond these workflows and production receiver/worker end-to-end certification remain pending.

All candidate assessment actions require an unexpired launch token and reject coding rounds until an isolated execution provider exists. Candidate responses use `Cache-Control: no-store`. Consent and start use conditional state updates: repeated consent before start preserves its timestamp, while competing starts yield one success and one conflict without resetting timing. Integrity-event writes serialize with submission and require an active, unexpired session. Launch-token expiry is checked again when committing these mutations; the browser timer is not an authorization boundary.

`PATCH /candidate/assessments/:token/draft` accepts `{ revision, answers, questionIndex }` for active sessions only. The revision must match `draftRevision` returned by the uncached session GET. A successful save returns `{ revision, savedAt }`; stale, closed, or concurrently changed sessions return 409 without overwriting the stored draft. Partial/empty answers are allowed, up to 100 entries, 10,000 characters per answer and 50,000 total; question indexes are 0–99. GET returns the active draft and original `startedAt` for resuming. Submission includes the latest `draftRevision`; clients without that field may submit only if no draft has ever been saved. Submission and draft saving serialize through the same assessment row. Successful submission atomically stores the final answers and clears the draft; draft text is never included in webhook payloads.

The global request ceiling is configurable with `API_RATE_LIMIT_MAX`; it defaults to 1,000/minute in development and 150/minute in production, while account and public API endpoints have stricter route-level limits. OAuth, pagination for internal workspace collections, and complete event versioning remain unimplemented.

## Nova recruiter copilot

All `/v1/nova/*` routes require an active browser session, workspace membership and `job.read`, `candidate.read`, and `report.read`. Organization API keys are not accepted. Responses are `Cache-Control: no-store`; writes retain the trusted-origin check.

- `GET /status`: explicit model availability, selected protocol/model and safe configuration reason.
- `GET /options?jobId=...&afterId=...`: roles and completed assessment pages, ordered by ID, never score.
- `GET /runs` and `GET /runs/:id`: the current user's workspace runs, safe traces, proposals and saved outcomes; not raw model transcripts.
- `POST /runs`: `{ message, selection: { jobId, selectedAssessmentIds, nextRoundId? }, parentRunId? }`; returns 202 with a persisted run ID. Maximum ten explicitly selected assessments; 20 requests per hour. An optional parent must be an owned READY/COMPLETED review for the same role. Follow-up creation atomically supersedes its pending proposal; past discussion never supplies current approval or evidence authorization.
- `POST /runs/:id/cancel`: cancels pending/review/proposal work, not committed invitations.
- `POST /proposals/:id/approve`: `{ fingerprint, confirm: true }`; requires `candidate.manage`, exact proposal ownership, current permissions and locked unchanged context. Expired or altered proposals cannot execute. Approval and invitation/credit effects are atomic; competing or repeated approval recovers the same encrypted outcome without another debit.

Prefix the paths above with `/v1/nova`. Model tools can retrieve evidence and prepare proposals, but cannot call approval. Runtime publication rechecks session and read permissions, including after an in-flight provider call. See [Nova setup and limitations](nova.md).
