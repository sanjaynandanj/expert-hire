# Assessment and scoring

The assessment schema recognizes resume screen, AI interview, human interview, coding test, and prompt assessment. Coding tests are currently fail-closed at invitation, launch, submission, and worker processing; they require a separately provisioned and reviewed isolated execution provider before use. The state machine is defined and tested in `packages/domain`.

Scores combine job requirements with a weight from 0–100. Every criterion result stores score, configured weight, rationale, and a concrete evidence excerpt or submission reference. A deterministic local evaluator will support repeatable tests. Production model output must be schema-validated and cannot issue a hiring decision.

Integrity events are stored independently from performance evidence and are advisory. They cannot trigger the rejected state.

Queued submission commits the validated evaluator response separately from structured answers before contacting Redis. Queue rejection or a three-second enqueue timeout returns HTTP 202 with `processing: pending_queue`; the assessment remains `PROCESSING`, not falsely failed. The non-production worker scans recoverable database submissions at startup and once per minute. Stable queue IDs prevent duplicate live jobs; retained finished jobs can be recreated without resetting the database retry budget.

Each evaluation claim increments a persistent attempt counter and receives a unique 60-second lease. Only an unexpired owner can complete queued work or release its claim. Crashed workers can be replaced after lease expiry; three exhausted claims lead to `FAILED`. Inline submissions are excluded from recovery. No manual replay API is provided for failed assessments. Legacy queued input can be adopted only when its original Redis job still contains the response; submissions predating durable storage cannot be reconstructed after Redis loss. The fixed lease is suitable for the current local evaluator, not a guarantee for future long-running production model calls. Production assessment execution remains disabled pending a reviewed provider.

New invitations store a versioned configuration snapshot: round type/title, duration, questions, proctoring/device settings, thresholds, job title/description, and named rubric weights. Empty authored question lists materialize the existing development fallback prompts rather than relying on later browser template changes; these prompts are not a validated job-specific assessment. Invitation creation locks the role and round consistently with editing. Candidate launch, inline/worker evaluation, and report retrieval use that frozen configuration, so later edits or retirement cannot change existing assessment context. Stored snapshots are validated; malformed or mismatched snapshots fail instead of silently using the live round.

Existing assessments without a snapshot use current configuration because their original settings cannot be reconstructed. Their report API marks `configurationSource: legacy_current`; new reports use `invitation_snapshot`. Assessment history lists also derive role/round labels from the snapshot when present. No migration fabricates historical questions or rubric values. Configuration snapshots contain no candidate responses or secrets and are not included in webhook event payloads. Independent assessment validity/adverse-impact review and an isolated coding provider remain required before production use.
